# 1.4.0 Release Notes

**Released:** 31 October 2026 · **Type:** Beta · **Image tag:** `1.4.0` · **Previous release:** 1.3.0 (24 September 2026)

1.4.0 makes every scan a **point-in-time record you can defend in an audit**: each run records what ran and who authorized it, its findings and reports are frozen when it finishes, and exports carry a fingerprint you can verify later. It also deepens the Wazuh endpoint integration, unifies Scanning into one module, and extends identity analysis to GCP and Azure.

:::warning[Read the upgrade notes first]
1.4.0 changes required `.env` values and adds services. Read [Upgrade notes](#upgrade-notes) before moving an on-premises install from 1.3.0.
:::

## Highlights

### Point-in-time evidence across every scan module

The same eight-step model now applies to Cloud (CSPM), Container, Kubernetes, Code and native Scanning:

- **Engagement record** — every scan records who authorized testing the target, the environment and the exclusions.
- **Provenance** — every run records the engine and version, its vulnerability database and how old it was, the arguments, the identity it ran as, and a hash of the raw tool output, which is kept.
- **Frozen results** — a run's findings and reports are frozen at completion, so a report on a past scan reproduces exactly what that scan found.
- **Fingerprinted exports** — issued PDF and HTML reports and exports are fingerprinted and can be verified later over the API (Word files are not fingerprinted); deletions are tombstoned and audited.
- **Compare runs** — finding by finding: new, fixed, unchanged. In the UI for cloud scans and native scans (against the previous run of the same target); over the API for code, container and Kubernetes scans. Container comparisons are digest-aware; a moved tag supersedes earlier results rather than marking them fixed.
- **No silent caps** — where a chart, summary or registry listing is truncated, the screen says so. Code findings are stored one row each, lifting the previous 3,000-finding storage cap (the ceiling is now `CODE_FINDINGS_MAX`, 50,000 by default).

### Wazuh endpoint security

- **Endpoint 360** — one in-platform page per agent; find an endpoint by name, IP or ID and share a link to it.
- **Fix first** — endpoint vulnerabilities ranked by triage priority, with a per-package roll-up and the Upgrade Impact view.
- **Alert triage in the platform** — grouped Wazuh alerts with stored state, tickets and SLAs; login anomalies reach the platform Alerts pipeline.
- **Agent health** — 30-day trends, endpoint agent coverage, a stale-agent cleanup flow (last-seen filter, CSV, retire / restore) and a Wazuh server health panel with a noise advisor.
- **File integrity noise reduction** — path-pattern groups, sensitive paths and an allowlist.
- **Cloud link** — agents are linked to the cloud VMs they run on (individually or in bulk), so exposure from the cloud side feeds endpoint triage. Network VAPT findings correlate with the Wazuh agent on the same host.
- **Compliance evidence** — Wazuh SCA results map to SCF controls as fleet evidence (failures only).

See [Wazuh Integration](../on-premises/wazuh-integration.md).

### Scanning

- **One Scanning module** — Assessments (App Scan), Targeted runs and New scan in one place; history grouped as a target tree instead of a flat list.
- **One progress model** for every scanning module, including cloud, container and Kubernetes scans.
- **Finished runs reach Vulnerability Management immediately.**
- **App Scan (DAST)** — exclusions, evidence, retest as the scan user, session checks and a second user; OAuth2 client-credentials / refresh-token authentication; browser-based login for multi-step and MFA logins (behind `DAST_BROWSER_AUTH`); pinned scanner and Nuclei template versions.
- **Network** — nmap depth: all TCP ports, UDP, `-Pn`, timing and OS detection. A Network / Infrastructure VAPT report on the shared reporting layer.

### Cloud, identity and attack paths

- **CIEM for GCP and Azure** — effective permissions from GCP IAM and Azure RBAC, capped by permission boundaries and SCPs on AWS; cross-account access; evaluation coverage shown in the UI.
- **Interactive security graph explorer** with blast radius from any node and an explanation when there are zero critical paths.
- **AWS reachability** evaluates route tables, NACLs and load balancers.
- **Custom policies** evaluated against the cloud inventory, with findings labelled in Findings.
- **Scope depth** — every enabled region, unassessed accounts in the estate and untagged resources are reported.
- Cloud findings name the IaC that owns the resource. Encryption-at-rest posture is collected during discovery.
- **Prowler upgraded 5.6.0 → 5.44.0**; Prowler checks map to SCF controls through Prowler's own compliance data. Each scanner engine is pinned to one version.

### Containers and Kubernetes

- Image findings know which workloads run the image; workload exposure feeds the triage score.
- Container sweeps say what they covered; two scan engines by default; one digest can be scanned with every tool.
- Kubernetes: one cluster entity, with discovered-but-not-connected clusters counted in coverage and named missing data sources instead of a false all-clear.

### Code security

- **SARIF 2.1.0 import** into Code Command Center, with suppressions carried as dispositions.
- **Branch selection** for scheduled repository scans.
- SBOM snapshot evidence: commit pin, SPDX export and export digests, VEX in the UI.
- GitHub App webhook delivery results shown in Offload.

### Vulnerability management, triage and compliance

- **One triage queue** across the unified findings lake; the Security Command Center AI agents work that same queue.
- **Investigation record** — one case file per finding across handoffs.
- **Risk exceptions tab** — request, approve / reject and revoke.
- **"Why this status"** — every GRC control status is traceable to the evidence behind it.
- Compliance API evidence for GCP and Azure accounts; one canonical evidence store with policy attestation.
- **Audit reports** — attestable PDF, frozen files and verification; format selection and evidence bundle in the UI.
- **Platform audit trail is hash-chained**, with durable writes and SIEM export.
- **Upgrade Impact** — a shared view for Code Command Center and Wazuh, with Linux fix enrichment from OSV distro advisories.

### Integrations and alerts

- **Greenbone OpenVAS over GMP**, with results in Vulnerability Management.
- **Splunk HEC and Syslog / CEF** forwarding of platform events.
- **GitHub Issues and GitLab Issues** as ticketing targets.
- **Microsoft Teams Workflows** (Adaptive Cards) and **Google Chat**.
- **Webhooks** screen with `alert.created` / `alert.updated` / `alert.resolved` events.
- **Capability health** — every integration source, why it stopped, and how to restore it.
- Daily SOC email digest in Alerts delivery settings.

### Threat intelligence and AI

- Intel is correlated onto findings automatically; public feeds are fetched once per platform. The PhishTank feed is retired (existing feed rows are disabled at startup).
- MITRE ATT&CK matrix from Wazuh and alert telemetry; a threat-intelligence lens over open CVEs.
- The AI assistant grounds answers in your team's own findings, assets and controls.
- Agentic fix: isolated sandbox runner, per-repository test settings (`.offload/agentic-fix.yml`). Opt-in — see [Upgrade notes](#upgrade-notes).

### Usability

- In-app **help guides** for every major module.
- Dashboard drill-downs from overview widgets, the severity donut, and cloud account / cluster cards into their findings.
- Deep-linkable module tabs; unknown values shown as **—**, never as 0.

## Upgrade notes

Take a backup before upgrading (see [Backups](../on-premises/deployment.md#backups)), then work through these in your `.env` before pulling the 1.4.0 images.

| Change | What to do |
| --- | --- |
| **`IMAGE_TAG` is required** | There is no `latest` default any more — `docker compose` refuses to start without it. Set `IMAGE_TAG=1.4.0`. |
| **`GHCR_OWNER` is required** | Set it to the registry owner given at onboarding. |
| **Docker socket proxy** | Scan workers now reach Docker through a restricted `docker-socket-proxy` service instead of mounting the socket directly. Set `DOCKER_GID` to the host's docker group (`stat -c '%g' /var/run/docker.sock`); the default of 996 is wrong on many hosts and the proxy then fails to start. |
| **Scheduled encrypted backups** | A new `backup` service backs up MongoDB and file volumes on a schedule. It **refuses to run** until you set `BACKUP_AGE_RECIPIENT` to an [age](https://age-encryption.org) public key (generate the key pair off the server and keep the private key safe). `BACKUP_ALLOW_UNENCRYPTED=true` overrides this; not recommended. |
| **Wazuh / OpenVAS credentials** | If you run the bundled Wazuh stack (`docker-compose.integrations.yml`), `WAZUH_API_PASSWORD` is required (`WAZUH_API_USERNAME` defaults to `wazuh-wui`). If you run the bundled Greenbone stack (`docker-compose.openvas.yml`), `OPENVAS_ADMIN_PASSWORD` is required (`OPENVAS_ADMIN_USER` defaults to `admin`). `docker-setup.sh` can generate per-server values. |
| **Encryption keys belong in `.env`** | Keys generated by the setup wizard are still read from the platform database as a migration bridge, but should be moved out: export them with `python -m scripts.remove_db_persisted_setup_secrets --export-env <path>`, put `CLOUD_ENCRYPTION_KEY` (and the other keys) in `.env`, then set `REQUIRE_EXTERNALIZED_SECRETS=true`. Without a key anywhere, saving credentials fails with *"Encryption key not found"*. |
| **Renamed / removed variables** | `ALERT_FINDING_MAX` → `ALERT_FINDING_BATCH` (now a batch size, not a cap). `WEBHOOK_SIGNING_SECRET` and `SCHEDULER_LOCK_TTL` are no longer read. |
| **Agentic fix is a compose profile** | The fix worker and its sandbox services start only with `--profile agentic-fix`. |
| **Prowler 5.44.0** | Cloud scan results after upgrading may differ from 1.3.0 because of new and changed Prowler checks; compare runs to see what moved. |

After `docker compose -f docker-compose.client.yml up -d`, check that every service is healthy with `docker compose -f docker-compose.client.yml ps`. Users will need to sign in again.

## Known issues

These are open in 1.4.0. The affected pages say so where the feature is described.

- **Blank values in `.env` override defaults.** `.env.example` ships about 100 optional settings as `NAME=`; in 1.4.0 a blank value replaces the built-in default, which breaks Nmap scans and the Kubernetes Trivy cache, among others. Comment out the blank lines after copying the template. See [Deployment & Operations](../on-premises/deployment.md#install).
- **Container Quick Scan fails on on-premises installs** (*Cannot connect to the Docker daemon*): it runs in the API service, which has no Docker access. Use `POST /api/container-registries/scan-image`, which runs on the scan workers. See [Image Scanning](../security-scanning/containers/image-scanning.md#quick-scan).

- **Scheduled Network and Container Registry scans fail** with `not_yet_implemented`, even though the scheduler still offers the "Weekly Network Scan" and "Weekly Container Audit" templates. Run these scans on demand. See [Scan Management](../security-scanning/scan-management.md).
- **Kubernetes token onboarding needs a kubeconfig.** The RBAC setup script says to paste a service-account token, but a bare token is rejected; build a kubeconfig from it. See [Onboarding Clusters](../security-scanning/kubernetes/onboarding-clusters.md).
- **Per-key API rate limits are not enforced.** `rate_limit_per_minute` is stored on each key; the limits that apply are per client IP. See [API conventions](../api-reference/conventions.md).
- **Compliance drift alert policies:** the "Info (all)" severity is treated as High and above, and the Teams channel option sends nothing (email, Slack and in-app work). See [Drift Detection](../compliance/drift-detection.md).
- **Docker Hub registries cannot be connected** (the connection test fails by design). Scan Docker Hub images by reference. See [Registries](../security-scanning/containers/registries.md).
